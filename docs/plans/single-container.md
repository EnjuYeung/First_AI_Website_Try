# 单容器部署方案

状态：已接受并完成实现。用户已确认全部方案（第一轮“都按照推荐”，Q4“交给现有网管”）。

## 目标

将当前项目的两个应用容器合并为一个，简化构建、部署与版本管理。

## 当前事实

- `docker-compose.yml` 定义 `web` 和 `backend` 两个服务。
- `Dockerfile` 构建前端并通过 Nginx 提供静态文件，`/api/` 请求转发给后台。
- `server/Dockerfile` 构建 Node 后台，后台同时运行 API、提醒调度、汇率调度和 Telegram 轮询。
- 当前入口为 `127.0.0.1:33001`，公网通过现有 1Panel OpenResty 访问。
- 后台继续使用项目根目录 `.env` 和 `Jan` 数据挂载；方案文档不记录配置值或用户数据。
- JSON 文件存储依靠单进程队列协调写入；同一 Telegram Bot 也只能由一个本项目后台实例轮询。

### 已核对的迁移边界

- 外层 OpenResty 已传递 Host、转发 IP 和协议；保留宿主入口即可保持现有站点代理配置。
- SPA 路径返回入口 HTML；未命中的 `/api/` 和 `/assets/` 返回 404。裸 `/api` 当前重定向到 `/api/`。
- 入口与 SPA 使用 `no-cache`，构建资源使用一年 `immutable`；普通 API 使用 `private, no-store`。
- 五项安全响应头目前主要由内层 Nginx 设置；去掉该服务需要由剩余 HTTP 服务承接。
- 内层 Nginx 还施加 9 MiB 总请求大小限制和 API 上游读取 30 秒无数据超时；这些与 JSON/文件自身的大小限制不同，不能遗漏。
- 容器内数据目录为 `/app/server/data`；保留该路径无需搬迁用户数据。当前使用 root 运行，改运行用户属于额外变更。
- 少一跳代理后需要验证真实客户端 IP、登录限流和 HTTPS 下的 Secure cookie。已在后台进程中仅查询两个非秘密配置字段：当前 `trustProxy` 为 `loopback, linklocal, uniquelocal`，端口为 `3001`，没有读取真实 `.env` 文件或输出其他配置。
- 当前 CI 分别运行前后端测试、审计和前端构建，未验证 Docker 镜像或容器 HTTP 行为。
- 前端 Alpine 构建固定 npm 11.6.1；后台使用独立 lockfile，最终镜像需要后台生产依赖及 `shared/`。

## 第一轮已确认决策

用户已回复“都按照推荐”：

1. 使用单个 Node 进程同时提供前端构建文件与 API，沿用外层 OpenResty。
2. 现有域名、入口端口、环境变量配置方式、数据挂载、功能与安全/缓存策略保持一致。

## Q4：网关约束的归属

已确认把原内层 Nginx 的以下约束迁移至已有 OpenResty 的当前站点配置，同时在仓库提供代理配置模板：

- 当前站点总请求体限制：`client_max_body_size 9m`。
- `/api/` 上游连接超时：`proxy_connect_timeout 5s`。
- `/api/` 上游响应读取超时：`proxy_read_timeout 30s`。

这需要调整当前站点的代理配置，但公网域名、证书和代理目标 `127.0.0.1:33001` 保持一致。静态文件路径继续沿用外层原有超时。

理由：JSON 解析器与 multer 分别限制 JSON 和上传文件，不能等价覆盖整个请求体；Node 的请求接收超时、socket 空闲超时也不能等价替代 Nginx 的上游响应读取超时。让现有网关继续承担这些职责，可保留原语义和独立于应用事件循环的限制。

约束：完整生产边界由一个应用容器及现有反向代理共同提供。其他环境部署时，应同时应用仓库中的代理配置模板；单独运行 Node 仍提供前端与 API，但总请求体与网关超时由外层代理保证。

依据：[Nginx 请求体上限](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)、[Nginx 代理读取超时](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)、[Node 请求接收超时](https://nodejs.org/docs/latest-v24.x/api/http.html#serverrequesttimeout)。

## 实施方案

### 镜像与进程

- 根 `Dockerfile` 采用 Node 24 Alpine 多阶段构建：前端严格安装与构建、后台生产依赖、最终 Node 运行镜像。
- 保留前端 npm 11.6.1 的锁文件兼容策略，继续使用前后端各自的 lockfile。
- 最终镜像包含 `/app/dist`、`/app/server` 和 `/app/shared`，不包含前端开发依赖、测试数据或生产秘密。
- 工作目录保持 `/app/server`，直接运行 `node server.js`；后台任务与 API 仍由同一个实例运行。
- Compose 统一为 `app` 服务、`subm` 容器、`first_ai_website_try:latest` 镜像，映射 `127.0.0.1:33001:3001`。
- 继续读取现有根目录 `.env`，挂载 `Jan:/app/server/data`，保持 `restart: always`；当前运行用户与数据权限保持一致。
- 沿用 JWT audience `subm-web`。它是令牌协议标识，容器改名不构成修改它的理由。

### HTTP 行为

- Express 通过绝对路径提供前端构建产物；本地 Vite 开发方式继续可用。
- `/assets/` 缺失返回 404；SPA 回退限定为前端 GET/HEAD，请求不会吞掉 `/api/` 或资源 404。
- 保留 `/api` 至 `/api/` 的重定向。
- 入口与 SPA 使用 `no-cache`；构建资源及现有用户上传沿用一年 `immutable`；普通 API 保留 `private, no-store`。
- 将现有五项安全响应头迁至应用 HTTP 层，覆盖静态、API 与错误响应。
- 保留 JSON、图标和壁纸自身的校验与大小限制；原网关约束移至现有 OpenResty。
- 校验真实 IP、伪造 XFF、HTTPS Secure cookie 与 CORS；当前生效的按地址范围信任代理配置可继续沿用。
